## 2. 系统架构

### 2.1 部署拓扑

```
          ┌──────────────┐         ┌──────────────────────────────┐
          │   GitHub     │──push──▶│  Vercel (静态托管 + CDN)      │
          └──────┬───────┘         │  village.example.com          │
                 │                 └──────────────┬───────────────┘
                 │ webhook                        │ fetch /api/*  (CORS)
                 ▼                                ▼
       (可选) CI 部署脚本              ┌──────────────────────────┐
                                       │ Caddy (api.example.com)   │
                                       │ - 自动 ACME 证书          │
                                       │ - /media/* 直接发文件      │
                                       │ - /api/* /ws/* 反代 :8000  │
                                       └────────────┬─────────────┘
                                                    │ 127.0.0.1:8000
                                       ┌────────────▼─────────────┐
                                       │ Uvicorn + FastAPI         │
                                       │ (Windows 服务, NSSM)      │
                                       └────┬────────────┬────────┘
                                            │            │
                                  ┌─────────▼──┐  ┌──────▼──────────────┐
                                  │ DB 文件/实例│  │ D:\village-data     │
                                  └────────────┘  └─────────────────────┘
```

**为什么前端与后端不同域？**
Vercel 只能托管静态资源，后端在自有 Windows Server，天然跨域。方案：

- 前端域名 `village.example.com`，后端 `api.example.com`。
- 后端 CORS 白名单精确配置，`allow_credentials=False`（用 Bearer Token 而非 Cookie，规避 SameSite 与跨域 Cookie 问题）。
- WebSocket 直连 `wss://api.example.com/ws?token=...`。

> 备选：把前端也放到 Windows Server 用 Caddy 托管，Vercel 只做备用。文档默认走 Vercel 方案，切换成本仅改一个环境变量。

> **备案期间（阶段 A/B）**：Caddy 那一层暂由 Cloudflare Tunnel 替代，前端用 `vercel.app` 默认域名，无需自有域名与备案。拓扑其余部分不变，切换步骤见 [06 文档 §2.5](./06-部署与运维方案.md)。

### 2.2 应用分层（后端）

```
api/v1/*.py            路由层：参数校验、鉴权依赖、调用 service
      │
services/*.py          业务层：事务边界、领域规则（如"仅作者或管理员可删"）
      │
models/ + db/          持久层：SQLAlchemy ORM / async session
      │
core/                  横切：配置、日志、异常、限流、安全
```

约定：
- 路由函数不写 SQL，只编排。
- 所有写操作在 `async with session.begin()` 内完成，异常统一抛 `AppError(code, message, status)`。
- 响应统一包装：`{"data": ..., "meta": {...}}`，错误：`{"error": {"code": "AUTH_INVALID", "message": "..."}}`。

### 2.3 前端分层

```
pages/          页面级容器（路由出口）
  └ features/   某个业务域的全部组件 + hooks + api
      └ components/  跨域通用 UI
api/client.ts   fetch 封装：baseURL、token 注入、401 刷新、统一错误 toast
```

数据流向：`page → useXxxQuery (TanStack Query) → api/xxx.ts → client.ts → FastAPI`

## 3. 鉴权与权限

### 3.1 Token 方案

| 项 | 设计 |
| --- | --- |
| Access Token | JWT，HS256，有效期 30 分钟，放 memory（Zustand）+ localStorage 兜底 |
| Refresh Token | 随机不透明字符串（不存 JWT），存 DB `refresh_tokens` 表，有效期 30 天，可撤销 |
| 刷新机制 | 401 → 拦截器静默调用 `/auth/refresh` → 重放原请求；并发请求排队只刷新一次 |
| PWA 长效登录 | Refresh Token 写入 IndexedDB（iOS PWA 下 localStorage 可能被清） |
| 退出 | 删除 DB 中该 refresh token |

### 3.2 RBAC

- 角色：`super_admin > admin > editor > member`
- 权限点用枚举，服务层判断而非仅靠路由装饰器（防止 IDOR 越权）：

```python
# 示例：删除文章
def can_delete_post(user, post) -> bool:
    if user.has_perm(Perm.CONTENT_MANAGE): return True
    return post.author_id == user.id and post.status != "archived"
```

- 对象级校验必须显式写：访问私聊消息、未公开相册、隐藏名片。

### 3.3 注册与风控

**三档注册模式**（`site_settings.feature.reg_mode`，后台实时切换）

| 值 | 含义 | 服务端行为 |
| --- | --- | --- |
| `open` | 自助注册（默认） | 不要求邀请码；填了则校验并计次 |
| `invite` | 邀请制 | 必须提供有效邀请码，否则 `INVITE_REQUIRED` |
| `closed` | 关闭注册 | 直接 `REGISTER_CLOSED`，仅后台建号 |

**审核**：新用户默认 `status=pending`（可登录浏览，不可写）。两种途径跳过审核：邀请码带 `auto_approve=1`，或全局开关 `feature.auto_approve=true`。

**邀请码设计**：`invite_codes` 表存 `code / max_uses / used_count / expires_at / auto_approve / note / disabled_at`。码短可读（如 `SHANGHEWAN-2026`），一码可多人用，方便按片区/家族分发；用完或过期自动失效。

**防刷**：
- 注册接口限流：同 IP 5 次/小时、20 次/天；
- 同一邮箱/手机号 24 小时内不可重复提交；
- 可选图形验证码（自绘 SVG，不依赖第三方服务）；
- 注册量异常（如 1 小时 > 20）时给超管发站内告警。

> 设计取舍：不做邮箱/短信验证码。村庄场景手机号在群里就是公开的，验证码成本与收益不成比例；用“邀请码 + 人工审核”把门，比机器验证更符合熟人社区。

## 4. 数据库策略

### 4.1 为什么 MVP 用 SQLite

| 维度 | SQLite (WAL) | PostgreSQL 16 |
| --- | --- | --- |
| 安装运维 | 零安装，单文件，备份=复制 | 需安装服务、建库建用户 |
| 并发写 | 单写者，够 50 并发读 + 低写 | 优秀 |
| 全文搜索 | `FTS5` 可用 | `tsvector` + 中文需 zhparser |
| 迁移成本 | 低 | - |

**结论**：一期用 SQLite（`check_same_thread=False` + WAL + `busy_timeout=5000`），写操作串行走 `asyncio.to_thread` 或直接同步 session。数据量超过约 10 万条或并发写明显冲突时迁 PostgreSQL。

### 4.2 迁移到 PG 的保障

- 全部使用 SQLAlchemy 2.0 声明式类型标注（`Mapped[str]`），不写方言专属 SQL。
- 唯一差异点集中在 `db/session.py` 的连接串与 `connect_args`。
- 迁移脚本：`alembic upgrade head` 到空 PG 库后，用 `python -m app.scripts.dump_restore` 走 CSV/JSON 分批导入。
- 避免使用 SQLite 特有能力：不用 `AUTOINCREMENT` 语义依赖、不用无类型列、时间统一 UTC `datetime`。

### 4.3 关键约定

- 主键：`id` 用 UUIDv7 字符串（可排序、便于将来分库/导出不撞号）。
- 时间：全部 UTC 存储，前端按 `Asia/Shanghai` 渲染。
- 软删除：`deleted_at IS NULL` 过滤（内容类表），物理删除仅管理员"彻底删除"。
- 计数冗余：`like_count`/`comment_count`/`view_count` 存主表，避免列表页 N+1 聚合。

## 5. 实时通信（WebSocket）

### 5.1 连接管理

```python
class ConnectionManager:
    # room_id -> {user_id: set[WebSocket]}   同一用户多端
    rooms: dict[str, dict[str, set[WebSocket]]]
    # user_id -> set[WebSocket] 用于私聊/通知推送
    users: dict[str, set[WebSocket]]
```

- 单进程内存管理（Uvicorn 单 worker）。**若将来上多 worker/多机，必须切 Redis Pub/Sub**，代码已按 `Broadcaster` 接口抽象，替换实现即可。
- 心跳：客户端每 25s 发 `ping`，服务端 60s 无心跳则断开。
- 重连：指数退避 1s/2s/4s/8s…上限 30s，重连成功后携带 `last_seq` 拉取断档消息。

### 5.2 协议（详见 04 文档）

```
客户端 → 服务端
{"type":"ping"}
{"type":"room.join","room_id":"..."}
{"type":"room.leave","room_id":"..."}
{"type":"message.send","client_id":"uuid","room_id":"...","kind":"text|image|video|file","payload":{...}}
{"type":"message.read","room_id":"...","seq":123}
{"type":"typing","room_id":"..."}

服务端 → 客户端
{"type":"pong"}
{"type":"message.new","room_id":"...","message":{...}}
{"type":"message.ack","client_id":"uuid","message_id":"...","seq":123}
{"type":"message.read","room_id":"...","user_id":"...","seq":123}
{"type":"presence","room_id":"...","online":["user_id",...]}
{"type":"notice","level":"info|warn","text":"..."}
{"type":"error","code":"RATE_LIMITED","message":"..."}
```

**可靠性三道保险**
1. `client_id`（前端 UUID）用于幂等：服务端以 `(room_id, client_id)` 唯一索引去重。
2. `room_seq` 单调递增房间内序号，客户端按 seq 补洞。
3. 消息落库成功才回 `ack`，客户端未见 ack 显示"发送中/失败重试"。

### 5.3 私聊实现

复用 `rooms(type='direct')` + `direct_key`（两个 user_id 排序后拼接的唯一键），避免多建一套表。

## 6. 文件与媒体处理

### 6.1 存储布局

```
D:\village-data\
├── uploads\
│   └── 2026\11\<uuid>.jpg            # 原图（仅登录可访问原始大小）
├── derived\
│   └── <uuid>\thumb.webp
│              small.webp
│              medium.webp
│              original.webp
├── videos\
│   └── <uuid>\index.m3u8
│              720p_000.ts ...
│              poster.jpg
│              source.mp4
├── attachments\ 2026\11\<uuid>_报告.pdf
├── backups\      village-20261103-0300.zip
└── logs\
```

- 通过 Caddy 直接暴露 `/media/derived/**`、`/media/thumbs/**`（公开、长缓存 `Cache-Control: public, max-age=31536000, immutable`）。
- 原图与附件走 FastAPI 鉴权后 `FileResponse`，不经 Caddy 直出，保证权限。
- 文件名一律 UUID + 白名单后缀，**不用原名**（防路径穿越与中文乱码）。

### 6.2 图片流水线

```python
# services/media/image.py（伪代码）
1. 校验 magic number（不信任扩展名、Content-Type）
2. Pillow 打开 → ImageOps.exif_transpose（方向纠正）
3. 若 HEIC → pillow-heif 注册后转换
4. 生成 4 档：320 / 640 / 1280 / 原始，统一 WebP（quality 82），保留 transparent
5. 读取 EXIF DateTimeOriginal → media.taken_at（用于年代排序）
6. **写回时剥离全部 EXIF/GPS**（隐私）
7. 失败重试 2 次，最终失败置 status='failed' 并记录日志
```

### 6.3 视频流水线

```
ffmpeg -i in.mp4 -vf "scale=-2:720" -c:v libx264 -preset veryfast -crf 23 \
       -c:a aac -b:a 128k -f hls -hls_time 6 -hls_playlist_type vod out/index.m3u8
ffmpeg -i in.mp4 -ss 00:00:01 -vframes 1 -vf scale=640:-2 out/poster.jpg
```
- 超过 10 分钟或 > 500MB 的视频：仅生成 480p，并在后台任务中排队（避免 CPU 打满）。
- 转码用 `subprocess` + `asyncio.create_subprocess_exec`，并发上限 2（信号量），Windows 上设置 `creationflags=CREATE_NO_WINDOW`。

### 6.4 上传流程选型

本方案不引入对象存储，采用**后端直传 + 分片**：

| 大小 | 方式 |
| --- | --- |
| < 8MB（图片） | `multipart/form-data` 单请求 |
| ≥ 8MB（视频/文件） | `POST /uploads/init` 拿 `upload_id` + 分片数 → 逐片 PUT → `POST /uploads/complete` 合并 |

好处：Windows Server 上无需额外服务；坏处：大文件占后端带宽。若日后改用 OSS/COS，只需替换 `uploads/init` 返回的 URL 为预签名直传地址，前端不用改。

### 6.5 限流与配额

- 单用户：图片 100 张/天，视频 10 个/天，总量 5GB（可后台调整）。
- 全站存储水位告警：达到磁盘 80% 时给管理员发站内通知并拒绝新视频上传。

## 7. 安全设计清单

| 风险 | 措施 |
| --- | --- |
| 密码泄露 | Argon2id 哈希；密码强度校验；登录失败次数限制 |
| 越权访问 | 所有对象级操作在 service 层校验 `owner/admin`；私聊校验 `room_member` |
| XSS | 富文本存 Tiptap JSON，渲染用白名单 schema（DomPurify + 自定义节点白名单）；禁止内联 `<script>`/`on*` |
| 上传恶意文件 | magic number 校验、后缀白名单、重命名为 UUID、存储目录不设可执行权限、附件强制 `Content-Disposition: attachment` |
| 路径穿越 | 只允许 UUID 文件名，拼接后 `Path.resolve()` 校验前缀 |
| CSRF | 使用 Bearer Token（非 Cookie），天然免疫；若后续改 Cookie 需加双提交 Token |
| 暴力注册 | 三档注册模式 + 管理员审核；邀请码可限制次数与有效期；IP 限流 + 可选图形验证码 |
| 敏感信息 | 在世人联系方式默认 `visibility='member'`；接口序列化按角色裁剪字段（用 Pydantic 不同 Schema） |
| 内容风险 | 敏感词、举报、管理员撤回、审计日志 |
| 依赖漏洞 | `pip-audit` / `npm audit` 纳入每周检查；锁定依赖版本 |
| 备份被加密 | 备份文件另存一份到异地（网盘/移动硬盘），定期验证可恢复 |

## 8. 可观测性

- **日志**：`loguru` 或标准库 `logging` JSON 格式，文件按天切分，保留 30 天；请求日志含 `request_id`、耗时、用户 ID。
- **健康检查**：`GET /healthz` 返回 DB 连通性、磁盘剩余、任务队列长度；配合 Windows 任务计划每分钟探测，连续 3 次失败则重启服务并写日志。
- **前端错误**：`window.onerror` + `unhandledrejection` 上报到 `POST /api/v1/client-errors`（采样 10%）。
- **业务看板**：后台首页指标卡（见 PRD M8）。

## 9. 性能优化要点

1. 列表接口全部游标分页（`before_id`），禁止 `offset` 深翻页。
2. 图片响应式：`<img srcset="...small.webp 640w, ...medium.webp 1280w" sizes="(max-width:768px) 100vw, 33vw">` + `loading="lazy"` + `decoding="async"` + 固定宽高比防抖动。
3. 首页记忆流聚合接口 `/feed` 一次返回混合内容摘要，避免前端多次请求。
4. TanStack Query 缓存 `staleTime` 60s；聊天用本地 IndexedDB 缓存。
5. 后端热点计数（点赞/评论数）写主表字段，不做实时聚合。
6. Gzip/Brotli 由 Caddy 与 Vercel 各自处理，FastAPI 侧只对 JSON 开 `GZipMiddleware`。
7. 前端路由级 `React.lazy` 分包，聊天与后台单独 chunk（后台不进主包）。

## 10. 技术风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Windows Server 上 ffmpeg/Pillow 兼容问题 | 转码失败 | 使用 ffmpeg 静态构建；Pillow 装预编译 wheel；上线前压测 20 个视频 |
| 单进程 WebSocket 内存管理 | 无法水平扩展 | 抽象 `Broadcaster` 接口，预留 Redis 实现；本期不做多进程 |
| Vercel 免费额度/国内访问速度 | 打开慢或被墙 | 备案域名 + 备用前端部署在同机房；静态资源 CDN 可切至国内 |
| SQLite 写锁 | 高峰期 500 | WAL + busy_timeout；写入串行化；监控 `database is locked` 日志 |
| 手机端视频上传中断 | 用户放弃 | 分片续传 + 本地草稿队列（IndexedDB） |
| 老照片扫描件巨大（>30MB） | 存储与流量 | 前端压缩（browser-image-compression）+ 后端限制 + 提供"上传后自动压缩"选项 |
| 项目长期无人维护 | 数据丢失 | 全量导出 + 备份异地 + 域名/CDN 长期续费提醒（写进交接文档） |
